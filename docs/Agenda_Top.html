01 / Executive overview

What we are building

Agenda is a native-feeling desktop application with a local service layer that lets one person run their life from a single dashboard. It organizes spaces such as Personal, Work, and Family, each with its own events, tasks, chores, lists, and people. It pulls in Google and Microsoft calendars and mail, and it keeps all data on the user's computer.

The first release has one owner per installation. Sharing with other people happens through the providers: a shared Google or Microsoft family calendar attached to the Family space shows everyone's events, and household members can be assigned chores as people without needing an Agenda login. Real multi-person sharing across devices needs a sync server and is deferred to a separately specified shared mode.

Desktop

Native shell, web UI

Tauri/Rust manages the app window, the backend sidecar, the per-launch secret, and OS integration. React/TypeScript provides the UI and widget registry.

Service

Local API boundary

A bundled Python/FastAPI sidecar owns domain rules, authorization, provider integrations, background jobs, and AI proposals.

Data

Single-file local database

SQLite in WAL mode stores application state, the durable job queue, and the outbox. No database server to install, upgrade, or supervise.

Extensibility

Typed widget registry

Built-in widgets are versioned registry entries with validated configuration. A manifest format for third-party widgets is reserved for later.

Non-goals for the first release

  • Requiring Docker or a separately installed database.
  • Hosting a cloud service or delivering remote multi-device synchronization.
  • Multiple Agenda login accounts or in-app sharing between people (see future shared mode).
  • Sending email or managing mailboxes; email is read-only triage.
  • Running arbitrary third-party code or launching a public widget marketplace.
  • Letting an LLM execute SQL, call unrestricted tools, or silently apply changes.
  • Supporting providers beyond Google and Microsoft at launch.
02 / Design principles

Constraints that shape implementation

PrincipleEngineering consequence
Local-firstCore tasks, local events, dashboard configuration, and cached provider data remain usable offline. Provider writes wait in a durable queue.
Authorization by defaultEvery domain query and command resolves the caller from the local session and is scoped to a space the caller can access.
Explicit ownershipThe owner holds identity and provider credentials; spaces own records; dashboard profiles only arrange views.
Provider adaptersGoogle and Microsoft APIs stay behind a common application interface; provider-specific behavior remains explicit.
Polling, not pushA local app has no public HTTPS endpoint for webhooks, so provider changes are detected by incremental polling with sync tokens or delta links.
Durable asynchronous workJobs are persisted, idempotent where possible, retryable, observable, and safe to resume after a restart.
Human approval for AIAI returns validated proposals. The application, not the model, authorizes and commits changes.
Build only what v1 usesWidgets are a typed in-code registry, not a plugin system; roles and memberships exist in the schema but v1 ships only the owner role.
Future network compatibilityUse stable UUIDs, explicit revisions, service-layer operations, and an outbox change log. Do not assume a shared database file is a sync protocol.

04 / Startup & lifecycle

Desktop and backend lifecycle

  1. Launch: Tauri initializes platform state, reads non-secret configuration, and generates a random 256-bit launch secret held only in memory.
  2. Backend spawn: start the packaged Python sidecar with a minimal environment and pass the launch secret over stdin. The sidecar binds to 127.0.0.1 on a free port and reports the port back on stdout.
  3. Database readiness: the sidecar opens (or creates) the SQLite file in the app-data directory and checks its schema version. If migrations are pending, it first writes a pre-migration snapshot, then migrates. A database newer than the app is refused with a clear message, not opened.
  4. Health handshake: Tauri polls /health/ready with a bounded timeout. On failure it shows recovery guidance (restore a backup, open the data folder, export diagnostics) rather than a blank window.
  5. Setup or unlock: on first run, show setup (owner name, default spaces). If app lock is enabled, show the unlock screen; otherwise open the last-used dashboard profile.
  6. Resume work: workers reclaim expired leases, resume retryable jobs, drain the outbox, and schedule an immediate provider poll to catch up on changes made while the app was closed.
  7. Shutdown: stop accepting new work, allow bounded completion, release leases, checkpoint the WAL, close connections, terminate the sidecar gracefully, then force-stop only after timeout.

06 / Security model

Local identity, authorization, secrets, and trust

Local identity and app lock

  • v1 has a single owner profile created at first run. The operating-system account is the main identity boundary; Agenda does not add a second account system on top of it.
  • Optional app lock: a passphrase hashed with Argon2id (unique salt, calibrated cost), throttled unlock attempts with increasing delay, and auto-lock after an idle period. While locked, every domain route returns 401 APP_LOCKED.
  • App lock is a privacy screen, not encryption. Anyone who can read the user's files can read the database unless at-rest encryption is adopted (open decision). Recommend OS disk encryption in the setup flow.
  • Never log passphrases, authorization headers, OAuth tokens, email bodies, or model prompts by default.

Local API boundary

  • Tauri passes the per-launch secret to the sidecar over stdin, never on the command line or in environment variables, which other local processes can read. The frontend gets it through a Tauri IPC command and sends it as a bearer token. It lives only in memory and changes every launch.
  • Bind to 127.0.0.1 on a random port; never 0.0.0.0.
  • Reject requests whose Host header is not 127.0.0.1:<port> (DNS rebinding). Restrict CORS to the exact Tauri origin.
  • Store provider refresh tokens in Windows Credential Manager, macOS Keychain, or the Linux Secret Service; if no vault is available, refuse to connect accounts rather than fall back to plaintext.
  • Create the database, WAL, and backup files with owner-only permissions.
  • Treat event descriptions, email content, calendar invites, and widget configuration as untrusted input, especially when included in an AI prompt.

Authorization policy

Every route resolves the actor from the session (in v1, always the owner) and checks access to the target space. Roles exist now so the policy code is written and tested once; in v1 every space has exactly one owner.

RoleReadCreate / edit / delete recordsSpace settings & membership
OwnerAll space dataYesYes, including archive/delete and role changes
Editor (shared mode)All space dataYes: events, tasks, lists, peopleNo
Viewer (shared mode)All space dataNoNo
Critical: the frontend is not an authorization boundary. Derive the space from the URL path, verify the target object actually belongs to that space, and never trust user or space IDs supplied in the request body.

Future shared mode

Sharing between people on different devices requires a sync server and a separate specification and threat model: TLS, remote authentication, invitations, revocation, rate limits, server-side authorization, sync conflict policy, and encrypted transport. The users and space_memberships tables, stable UUIDs, revisions, and the outbox are kept so that mode can be added without re-keying data. Do not simply change the local bind address.

Concurrency contract

Mutable resources carry a monotonically increasing application revision. Clients send If-Match with the expected revision. If it has changed, return 409 with safe metadata for reload/reconciliation. Provider ETags and sync tokens are stored separately from Agenda's revision.

Use distinct messaging patterns rather than one universal bus:

Request / response

Frontend → REST API → application service. Use for user-initiated reads and writes. Return a resource or accepted job ID.

Job state machine

queued → leased → succeeded, with retryable failure returning to queued after backoff. Permanent failures become dead_letter. Cancellation and supersession are explicit states where supported.

-- Claim one job. Short write transaction; never held across a network call.
BEGIN IMMEDIATE;
UPDATE jobs
   SET state = 'leased', lease_until = :lease_until, attempts = attempts + 1
 WHERE id = (
   SELECT id FROM jobs
    WHERE (state = 'queued' AND available_at <= :now)
       OR (state = 'leased' AND lease_until < :now)
    ORDER BY available_at
    LIMIT 1)
RETURNING *;
COMMIT;
  • Workers run as asyncio tasks inside the single sidecar process, so there are no cross-process claim races. SQLite allows one writer at a time: keep write transactions short.
  • Lease expiry makes interrupted jobs reclaimable after a crash.
  • Use exponential backoff with jitter, honor provider Retry-After, and cap retries.
  • Handlers must be idempotent or record a deduplication key before external side effects.
  • Serialize jobs per calendar source so writes to the same provider event never race.
  • Expose safe status, progress, timestamps, and error category, not raw credentials or provider response dumps.
10 / Calendar synchronization

Polling, mapping, and two-way sync

Sync ships in two stages: read-only import first (Phase 3), then two-way writes with conflict handling (Phase 4). A calendar source stays read-only unless the user switches it and the provider grants write access.

Change detection

  • Google push channels and Microsoft Graph subscriptions need a public HTTPS endpoint, which a local app does not have. Use incremental polling instead.
  • Google: events.list with syncToken; on 410 Gone, discard the token and run a full resync that reconciles by event_mappings without duplicating events.
  • Microsoft Graph: calendarView/delta with the stored deltaLink; on an expired link, full resync the same way.
  • Cadence: every 5 minutes while the app is open, immediately on launch, on window focus after being idle, and right after a local write. Back off on 429/5xx. Closing the window hides Agenda to the system tray, so sync and reminders keep running until the user quits from the tray; Agenda starts at login (ADR 0001).

Calendar-to-space mapping

When an account is connected, the user picks which provider calendars to import and which space each belongs to (for example, the shared "Family" Google calendar → Family space). Imported events take that space. Moving a source to another space moves its events.

Two-way write sequence

  1. User edits an event in Agenda. The transaction bumps the event revision and writes an outbox row.
  2. The sync worker claims the write job and sends it with the stored ETag/changeKey as a precondition (If-Match).
  3. If the provider accepts, store the new ETag and last_synced_revision.
  4. If the precondition fails because the provider changed independently, fetch the remote version and store both snapshots as a conflict; do not overwrite silently.
  5. Agenda shows local and provider versions. User chooses local, provider, or keep both.
  6. Resolution is committed with the expected revisions, and a new idempotent job reconciles the provider and mapping.

Conflict model

SyncConflict {
  id: UUID
  event_id: UUID
  calendar_source_id: UUID
  local_snapshot: JSON
  remote_snapshot: JSON
  local_revision: int
  remote_version: string | null   # ETag/changeKey
  detected_at: datetime
  status: "open" | "resolved" | "superseded"
  resolution: "keep_local" | "keep_remote" | "keep_both" | null
  resolved_at: datetime | null
}

Provider adapter responsibilities

  • OAuth as a public desktop client: system browser (embedded webviews are blocked by Google), PKCE S256, one-time state, and a loopback redirect to http://127.0.0.1:<port>. The desktop "client secret" is not confidential and must not be relied on.
  • Request the narrowest scopes per stage: read-only calendar scopes for import; event write scopes only when the user enables two-way sync.
  • Token refresh, revocation on disconnect, and credential-vault integration; mark the account needs_reauth on invalid_grant instead of retrying.
  • List calendars, fetch changes, interpret cancellations and tombstones, and persist sync cursors.
  • Translate provider events into the canonical model (RRULE series + exception rows) without losing important provider metadata.
  • Handle rate limits, pagination, recurrence exceptions, all-day dates, time zones, attendees, and cancellation semantics.
Important edge cases: recurring event edits ("this", "this and following", "all"), DST transitions, moved events, duplicate imports, deleted events, offline edits, token expiry, provider outages, and attendee changes need explicit tests. "Keep both" must create distinguishable records and mappings rather than a duplicate loop.
11 / Email integration

Read-only mail triage

Email in v1 answers "what needs my attention?" on the dashboard: unread counts, recent headers, and a button that opens the message in the provider's web app. Agenda does not send, delete, archive, or label mail.

  • Poll message headers on the same scheduler as calendars (Gmail history.list with historyId; Graph messages/delta).
  • Cache headers only (email_messages). Bodies are fetched on demand, sanitized (render as text or in a sandboxed frame with remote content blocked), and never stored or logged.
  • Optionally attach a mail account to a space so the Work dashboard shows work mail only.
  • Email content is untrusted input; it is not passed to the AI planner unless the user selects a specific message.

Provider constraints

ProviderScopeConstraint
Microsoft GraphMail.Read (delegated)User-consentable; no third-party security assessment. Publisher verification recommended before public release.
Gmailgmail.metadata or gmail.readonlyBoth are restricted scopes. A public release requires Google verification plus an annual third-party security assessment (CASA). For personal use, keep the OAuth app in "Testing" with named test users. In that status, refresh tokens expire after 7 days and the user must reconnect weekly.
Ordering: build the Microsoft mail adapter first. Gmail ships under Testing status for personal use; decide whether to pay for a CASA assessment before any public Gmail release.
12 / Widget system

Typed built-in widget registry

In v1, widgets are built-in React components registered in a typed TypeScript registry. There are no manifest files, no dynamic loading, and no backend widget endpoints. The backend stores layout and configuration in dashboard_profiles; the registry validates it.

export interface WidgetDefinition<Config> {

  version: number;             // bump when the config shape changes

  configSchema: z.ZodType<Config>;
  defaultConfig: Config;
  migrateConfig?: (old: unknown, fromVersion: number) => Config;
  layout: { minW: number; minH: number; resizable: boolean };

}

export const widgetRegistry = [
  upcomingEvents, tasksAndChores, lists,     // Phase 2
  notifications, emailSummary,               // Phase 5
  aiProposals,                               // Phase 7
] as const;

Widget lifecycle

  1. Load the dashboard profile.
  2. Look up each widget ID; an unknown ID renders a "widget unavailable" placeholder instead of failing the dashboard.
  3. Migrate old configuration, then validate it against the schema; fall back to defaults on failure.
  4. Render inside its own error boundary.
  5. Fetch data through the generated API client for the profile's selected spaces.
  6. Persist layout and configuration changes with optimistic concurrency.

Widget rules

  • Stable widget IDs; never reuse an ID for a different widget.
  • Configuration changes bump version and ship a migration.
  • Widgets hold no authority: every API call goes through the same session and space checks as the rest of the UI.
  • One broken widget must never crash the dashboard.
  • Third-party widgets (manifest, capability model, sandboxed iframes, widget-sdk) are deferred until there is a concrete need.

Hard constraints

14 / Persistence & backup

Migrations, backups, and recovery

Database rules

  • The database lives in the OS app-data directory (%APPDATA%\Agenda, ~/Library/Application Support/Agenda, $XDG_DATA_HOME/agenda) with owner-only permissions.
  • Use versioned Alembic migrations and its version table; never rely on ORM auto-create. Take a snapshot before every migration.
  • Use transactions for domain mutations together with their outbox and job inserts.
  • Use foreign keys, unique constraints, and indexes for correctness, not only application checks.
  • Use tombstones where provider synchronization or audit retention requires it.
  • Use UTC timestamps and keep named time zones where calendar semantics need them.

Backup workflow

  1. Create consistent copies with SQLite's online backup API or VACUUM INTO; both are safe while the app is running.
  2. Keep rolling automatic snapshots (e.g. daily for 7 days, plus pre-migration) in the app-data directory.
  3. Manual backups go to a user-chosen location as one file plus a manifest (app version, schema version, created_at), optionally encrypted with a passphrase.
  4. Provider tokens are not in the database, so they are never in backups. After a restore on a new machine, the user reconnects accounts.
  5. Restore: run PRAGMA integrity_check, verify the schema version is not newer than the app, pause workers, swap the file, and restart the sidecar.
  6. Run automated restore tests in CI and verify core queries afterwards.
A backup is not considered verified until a restore test succeeds. Include restore drills in release qualification, not just backup creation tests.

17 / Lifecycle phases

Development lifecycle from prototype to release

Each phase ends in a usable state and maps one-to-one to a milestone in section 18. Phase 3 is the personal MVP: the point where Agenda replaces opening Google Calendar and a to-do app every morning.

Phase 0

Architecture validation

Goal: retire the packaging and process-lifecycle risks before writing features.

  • Tauri spawns the bundled Python sidecar, passes the launch secret, and supervises it through crash and shutdown.
  • Sidecar creates and migrates a SQLite file in the app-data directory.
  • Choose the sidecar bundler; sign and notarize on macOS; check Windows SmartScreen/antivirus behavior; measure cold start.
  • CI builds installers on all three OSes.

Exit gate: on every OS, the packaged app creates a record, restarts, and reads it back.

Phase 1

Personal core

Goal: the local data foundation.

  • First-run setup, owner profile, optional app lock, local API boundary checks.
  • Spaces, people, tasks and repeating chores, lists, local events with the recurrence model.
  • Error envelope, optimistic concurrency, job queue, outbox worker, audit log.

Exit gate: data persists across restarts; every route rejects a missing secret; cross-space substitution tests pass; job crash/retry tests pass.

Phase 2

Dashboard

Goal: the customizable desktop experience on local data.

  • Dashboard profiles, typed widget registry, layout persistence.
  • Starter widgets: upcoming events, tasks & chores, lists.
  • Widget error boundaries, config migration, keyboard accessibility.

Exit gate: the owner can build Personal, Work, and Family dashboards that survive restarts, and a broken widget cannot take down a dashboard.

Phase 3

Google Calendar, read-only · personal MVP

Goal: see real calendars in Agenda.

  • Desktop OAuth flow, credential vault, account management.
  • Calendar-to-space mapping, incremental polling with sync tokens, full resync on 410.
  • Import of recurrence, exceptions, all-day events, time zones, and cancellations.

Exit gate: import stays correct through DST, recurrence exceptions, deletions, and forced resyncs, with no duplicate events.

Phase 4

Two-way sync and Microsoft

Goal: edit provider events from Agenda safely.

  • Provider writes with ETag preconditions, event mappings, offline write queue.
  • Conflict detection and resolution UI (keep local, remote, or both); recurring edit scopes.
  • Microsoft Graph calendar adapter (read-only, then two-way) against the same contract suite.

Exit gate: both providers pass the contract suite and no tested conflict path silently overwrites data.

Phase 5

Notifications and email

Goal: Agenda tells you what needs attention.

  • Reminder planner, OS notifications through Tauri, in-app inbox, quiet hours.
  • Read-only email triage: Microsoft mail first, Gmail under Testing status.
  • Notification and email summary widgets.

Exit gate: reminders fire correctly across restarts and time-zone changes; email bodies are never persisted or logged.

Phase 6

Release hardening

Goal: something you could hand to someone else.

  • Backup/restore UI, automatic snapshots, diagnostics bundle.
  • Installers, auto-update, upgrade migrations from every released version.
  • Security review, dependency scanning, SBOM; decide on Google verification.

Exit gate: restore drill and install/upgrade smoke tests pass on all supported OSes.

Phase 7

Optional local AI

Goal: generate safe, reviewable planning proposals.

  • Provider interface, local runtime configuration, authorized context builder.
  • Structured proposals, deterministic validation, approval and audit, proposals widget.
  • Prompt-injection and stale-proposal tests.

Exit gate: AI can be disabled without breaking core features; no proposal applies without user approval.

Future

Shared mode · not scheduled

Multiple people sharing spaces across devices. Requires a sync server, remote authentication, invitations, and its own specification and threat model. Start only after Phase 6.

Decisions to make before implementation of the affected feature

  • Sidecar bundler: PyInstaller, Nuitka, or a standalone Python build plus virtual environment (Phase 0).
  • Recurring event model details: how RRULE series, exceptions, and the "this and following" split are stored (Phase 1).
  • At-rest database encryption (SQLCipher) versus relying on OS disk encryption (Phase 1).
  • Exact OAuth scopes per stage, and whether to pursue Google verification and CASA (Phases 3–6).
  • Polling cadence (Phase 3). Tray behavior is decided: keep running in the tray, start at login (ADR 0001).
  • Backup encryption and passphrase recovery behavior (Phase 6).
  • When live UI updates justify Server-Sent Events over polling.
20 / Release acceptance

Definition of done

  • Application installs and launches on every supported OS without Docker or a separately installed database.
  • Backend is reachable only from the Agenda frontend through the loopback launch-secret boundary.
  • The owner can organize personal, work, and family spaces, assign chores to people, and optionally lock the app.
  • Every space-scoped API route has authorization and negative access tests.
  • Tasks and Agenda-owned events survive restart and offline operation.
  • Dashboard layouts and widget configuration persist, and broken widgets fail in isolation.
  • Google and Microsoft sync jobs are durable, retryable, and idempotent where required.
  • Conflicts are visible and users can keep the local version, provider version, or both.
  • Email is read-only and message bodies are never stored.
  • AI is optional, local-only, proposal-based, and requires explicit approval.
  • Backups can be restored into a clean install and verified.
  • Logs and diagnostics do not expose passphrases, tokens, or private content by default.
  • Database migrations, upgrade paths, and failure recovery are documented and tested.
Final engineering principle: ship a small, secure, observable end-to-end product first. Add integrations and AI only after the local API boundary, persistence, and job-processing foundations have proven reliable.
